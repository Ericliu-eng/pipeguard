# PipeGuard v1.0.0

PipeGuard v1.0.0 is the first stable release of the lightweight pipeline-monitoring
platform. It expands the synthetic demo into a service that can receive completed runs
from real pipelines, evaluate historical quality signals, retain searchable run history,
and provide deterministic incident guidance.

## Highlights

- Report real pipeline executions through authenticated `POST /runs` requests, including
  timing, row counts, errors, and pipeline-evaluated quality checks.
  [de-lakehouse-pipeline](https://github.com/Ericliu-eng/de-lakehouse-pipeline) is the first
  producer: each run of its CLI orchestrator reports here.
- Retry reports safely with a per-pipeline `external_run_id`: identical retries return the
  existing run with `200`, while conflicting payloads return `409`.
- Keep execution outcome and data quality separate through `status` and `quality_status`.
- Detect row-count anomalies using healthy historical runs stored by PipeGuard.
- Filter and page through run history with exact pipeline-name matching, execution and
  quality filters, deterministic ordering, accurate totals, and KPI summaries.
- Explain each failed check in terms of what it measures. A collapsed row count points at
  upstream truncation or throttling, not at nulls and duplicates; checks commonly reported by
  external pipelines (`not_null`, `unique`, `range`, `foreign_key`) are covered too.
- Inspect run KPIs, quality checks, history, and stored incident analyses in the updated
  Streamlit dashboard.
- Reproduce successful, execution-failure, and data-quality-failure scenarios with the
  bundled synthetic demo pipeline.
- Apply configurable per-pipeline retention and remove dependent checks and analyses with
  pruned runs.

## Production

- FastAPI and Streamlit ship as separate Docker images, with Docker Compose for local use.
- The API container applies Alembic migrations before starting Uvicorn.
- The hosted API uses PostgreSQL; local development and the default test suite use SQLite.
- `/health` executes a real database probe and returns `503` when persistence is unavailable.
- Both the migration engine and the application engine give up on an unreachable database
  after `DATABASE_CONNECT_TIMEOUT` seconds (default `10`), so a dead database fails the boot
  with an error instead of hanging it.
- External ingestion fails closed when `INGEST_API_KEY` is unset and compares keys in
  constant time.
- GitHub Actions runs Ruff and the full suite against both SQLite and PostgreSQL 18.

## Quality

- Four built-in checks cover null rate, duplicate rate, freshness, and historical row-count
  drops.
- Run-level quality is summarized as `PASS`, `WARN`, `FAIL`, or `NOT_EVALUATED`.
- Failed executions are not misclassified as zero-row quality incidents, and failed-quality
  runs do not contaminate future row-count baselines.
- External reports validate non-negative row counts, timezone-aware timestamps, and
  chronological start/finish ordering.
- The suite contains 58 passing tests covering APIs, ingestion, retry conflicts, health
  checks, migrations, retention, database configuration, quality checks, incident analysis,
  and paginated history. Data migrations are tested on rows in the old format, and a
  regression test confirms migrations give up on an unresponsive database.

## Upgrade notes

- **Breaking API change:** `likely_causes` and `recommended_steps` in incident analyses are
  now JSON arrays. They were previously strings containing encoded JSON, so clients that
  decoded them with a JSON parser must read them directly instead.
- Migration `0003` converts analyses already stored in the old format; run
  `alembic upgrade head` (the API container does this on start).
- New analyses report `model_name` as `rule-based`; earlier ones keep `rule-based-fallback`.
- New setting: `DATABASE_CONNECT_TIMEOUT`.

## Known limits

- The bundled demo pipeline uses synthetic rows; real pipelines integrate through the REST
  API rather than packaged SDKs or orchestrator-specific adapters.
- Incident analysis is deterministic and rule based; it does not call a live LLM.
- Ingestion uses one shared API key. User accounts, RBAC, multiple keys, and rate limiting
  are not yet included.
- Quality thresholds are configured through environment variables rather than the dashboard.
- Offset pagination can shift when new runs are inserted while a user browses later pages.
- PipeGuard detects database outages through `/health`, but does not yet deliver alerts or
  monitor that endpoint externally.
